# Практическое задание «Анализ уязвимостей в веб-приложении»

**Объект исследования:** Visual Tab Manager (VTM) — браузерное расширение (WebExtension, Manifest V3)
для визуального переключения вкладок с сохранением превью выбранных элементов страницы.
Репозиторий: `Frugd/vtm`. Кодовая база ~5200 строк JS/CSS/HTML.

**Компоненты:**

| Компонент | Файл | Роль |
|---|---|---|
| Service worker (background) | `background.js` (1040 строк) | IndexedDB, `storage.sync`/`storage.local`, захват вкладок, обработчик сообщений |
| Content script автозахвата | `content/content-autocapture.js` | Периодически ищет элемент по CSS-селектору и просит фон сделать скриншот |
| Content script пикера | `content/content-picker.js` | Инжектится через `scripting.executeScript`, выбор элемента мышью |
| Popup | `popup/popup.html`, `popup.js` | UI действий |
| Manager | `manager/manager.html`, `manager.js` | Галерея превью, настройки, правила |
| Shared UI | `shared/ui.js` | i18n, темы, тосты |

## Задание № 2. Практическое исследование VTM

Методика: ручной аудит исходного кода (white-box), анализ `manifest.json` и модели разрешений,
трассировка потоков данных «страница → content script → background → IndexedDB → manager UI»,
проверка мест вывода данных в DOM, нагрузочные рассуждения по хранилищу и захвату.

### 2.1 Аутентификация и авторизация

Классической аутентификации (логин/пароль) в расширении **нет** — субъект один, это владелец
профиля браузера. Роль «границы доверия» играет не сессия, а **модель разрешений браузера**
и **проверка отправителя сообщений**.

Что реализовано корректно:
* `manifest.json` не содержит `externally_connectable`, значит произвольные веб-страницы
  не могут напрямую слать сообщения в service worker.
* Широкий доступ к сайтам вынесен в `optional_host_permissions: ["<all_urls>"]`, то есть
  запрашивается по согласию пользователя, а не выдаётся при установке — это правильная
  реализация принципа наименьших привилегий.
* Content script автозахвата регистрируется динамически (`syncAutoCaptureContentScript`)
  и снимается при отзыве разрешения (`permissions.onRemoved`).

Найденные проблемы:

**V-1 (Средний). Отсутствие валидации отправителя в обработчике сообщений.**
`background.js:750` — обработчик принимает любое сообщение и сразу маршрутизирует его:

```js
browser.runtime.onMessage.addListener((msg, sender, sendResponse) => {
  handleMessage(msg, sender).then(sendResponse)...
});
```

`sender.id`, `sender.origin`, `sender.url` не проверяются. Любой content script на любой
странице (а через него — внедрённый на странице XSS-код, который может дотянуться до
изолированного мира лишь косвенно, но в Firefox — и другое расширение через доступный ID)
получает полный привилегированный API: `GET_ALL_THUMBNAILS` (все скриншоты всех сайтов
пользователя), `GET_ALL_SELECTORS`, `CLEAR_ALL_THUMBNAILS`, `OPEN_MANAGER`, `SWITCH_TO_TAB`.
Это A01 (Broken Access Control) — нарушение границы доверия между «недоверенной страницей»
и «привилегированным фоном».

**V-2 (Средний). Отсутствие авторизации по объекту: доступ ко всем данным из любого контекста.**
Скомпрометированная вкладка `evil.com` может запросить
`{type:"GET_ALL_THUMBNAILS"}` и получить JPEG-превью страниц банка, почты, корпоративных
систем — фактически IDOR-подобная утечка: нет проверки, что запрашивающий контекст
имеет отношение к запрашиваемому hostname.

**V-3 (Низкий/Средний). Захват экрана привязан только к «активности» вкладки.**
`CAPTURE_AND_SAVE` проверяет `tab.active`, но не проверяет, что расширению выдан
host permission именно на этот origin. Любая активная вкладка, где по каким-то причинам
исполняется скрипт расширения, может инициировать `captureVisibleTab` — а это скриншот
видимой области, то есть потенциально данные другого происхождения (баннеры с 2FA-кодами,
содержимое PDF, приватные сообщения).

### 2.2 Управление сессиями

Cookies и серверные сессии в расширении **не используются**, атрибуты `Secure`/`HttpOnly`
неприменимы. Роль состояния сессии играют:

| Хранилище | Что лежит | Область видимости | Оценка |
|---|---|---|---|
| IndexedDB `vtm-thumbnails` (в контексте расширения) | `url`, `hostname`, `title`, `dataUrl` (JPEG base64), `timestamp` | Только расширение | Не шифруется, лежит на диске в профиле |
| `storage.sync` (ключи `vtm_sel_*`, `vtm_rules`) | CSS-селекторы и ключевые слова по доменам | **Синхронизируется в облако браузера** | Утечка карты посещаемых доменов |
| `storage.local` (`vtm_window_state`, настройки) | Геометрия окна, язык, тема | Локально | Норма |

**V-4 (Высокий). Незашифрованное хранение скриншотов приватных страниц.**
`background.js:38 saveThumbnail()` кладёт в IndexedDB полный `data:image/jpeg;base64,...`
без какого-либо шифрования и без TTL. Профиль браузера читается любым процессом,
работающим от имени пользователя (стилер-малварь, синхронизация папок, бэкап, форензика
изъятого ноутбука). Аналог A02 Cryptographic Failures: чувствительные данные at-rest в
открытом виде. Усугубляется тем, что нет ограничения на количество записей и нет
автоочистки — история превью копится бессрочно.

**V-5 (Средний). Утечка списка доменов в облачную синхронизацию.**
`saveSelector()` (`background.js:137`) пишет в `browser.storage.sync`, то есть ключи вида
`vtm_sel_mail.corp.example.com` уходят на серверы Mozilla/Google и «размножаются» на все
устройства пользователя, включая недоверенные. Персональные данные (карта посещаемых
ресурсов) покидают устройство без явного согласия.

**V-6 (Низкий). Нет инвалидации «сессии» состояния.**
`recentAutoCaptures` и `inFlightAutoCaptures` живут в памяти воркера; при перезапуске
дедупликация сбрасывается, что приводит к повторному захвату — не безопасность, но
предсказуемость поведения и лишняя запись данных.

### 2.3 Обработка пользовательского ввода (SQLi / XSS)

**SQL-инъекции:** реляционной СУБД нет, запросы к IndexedDB строятся через `objectStore.put/get`
с ключом, а не конкатенацией строк — **классическая SQLi неприменима**. Однако есть
аналог — «инъекция в хранилище»: ключом записи служит подконтрольный странице `url`
(`saveThumbnail`: `url: data.url || String(Date.now())`), а `msg.hostname` берётся из
сообщения content script и никак не сверяется с реальным `sender.tab.url`.
Это **V-7 (Средний): подделка записей в хранилище** — вредоносная страница может записать
превью под чужим hostname (спуфинг в галерее manager: карточка выглядит как «Сбербанк»,
но ведёт на фишинговый URL) или затереть чужие записи, подобрав ключ.

**XSS.** Проверены все точки вывода в DOM:
* поиск по `innerHTML`, `outerHTML`, `insertAdjacentHTML`, `document.write`, `eval`,
  `new Function`, `createContextualFragment` по всей кодовой базе — **совпадений 0**;
* заголовки и URL выводятся через `textContent` / `replaceChildren` с построением
  DOM-фрагмента (`manager.js:579`, `createHighlightedFragment` с `document.createElement("mark")`),
  подсветка поиска сделана безопасно;
* i18n подставляется через `element.textContent = t(...)` (`shared/ui.js:299`).

Итог: **инъекция HTML/JS в UI менеджера не воспроизводится**. Это сильная сторона проекта.
Остаточные риски:

**V-8 (Средний). Инъекция в SVG-фавиконку.** `manager.js:783 buildFaviconDataUrl()` собирает
SVG конкатенацией строк и подставляет туда `letter`, полученный из `hostname`:
```js
const letter = String(hostname || "V").trim().charAt(0).toUpperCase() || "V";
const svg = `<svg …><text …>${letter}</text></svg>`;
```
Сейчас берётся ровно один символ, поэтому «сломать» разметку нельзя, но паттерн опасен:
любое изменение (например, показывать 2–3 буквы) мгновенно даёт XSS-вектор,
т.к. `hostname` в записи подделываем (см. V-7). Классифицируется как уязвимость дизайна.
Кроме того, SVG подставляется в `img.src` как data:URL — здесь скрипт не выполнится,
но при переносе такого же кода в `innerHTML` — выполнится.

**V-9 (Средний). Инъекция CSS-селектора (selector injection).**
`content-autocapture.js:129` выполняет `document.querySelector(selector)`, где `selector`
приходит из `storage.sync`, а туда попадает из пикера (`SELECTOR_PICKED`) и из формы
настроек менеджера (`SAVE_DOMAIN_CONFIG`) **без валидации синтаксиса**. Некорректный
селектор бросает исключение, специально сконструированный — заставляет расширение
скриншотить произвольную область (например, элемент с одноразовым кодом).
Плюс `:has()`/сложные селекторы на большом DOM — вектор для ReDoS-подобной деградации (см. 2.5).

**V-10 (Низкий). Открытие URL из хранилища без проверки схемы.**
`manager.js:607` и `manager.js:654`: `browser.tabs.create({ url: thumb.url })`, где `thumb.url`
пришёл из сообщения. Схема не фильтруется — при подделке записи (V-7) в галерее появляется
карточка с `javascript:`/`data:` URL. Современные браузеры блокируют `javascript:` в
`tabs.create`, но `data:`/`file:` сценарии и фишинговые редиректы остаются.

**V-11 (Информационный). Логирование чувствительных данных.**
`background.js` содержит десятки `console.log` с URL и длинами скриншотов
(`"[VTM] CAPTURE_AND_SAVE started for", msg.hostname`). В продакшене это утечка
телеметрии в консоль и нарушение A09 (логирование секретов).

### 2.4 Безопасность компонентов

| Аспект | Факт | Оценка |
|---|---|---|
| Сторонние зависимости | `package.json`, `node_modules`, CDN-скрипты **отсутствуют**; весь код собственный, vanilla JS | Отлично: поверхность supply-chain минимальна, известных CVE нет |
| Manifest version | MV3 (`manifest_version: 3`) | Актуально; наследуется строгий дефолтный CSP расширения (без `unsafe-eval`) |
| Явный CSP | В манифесте `content_security_policy` **не задан** | Средний: полагаемся на дефолт. Рекомендуется зафиксировать явно |
| `web_accessible_resources` | Открыт только `content/content-picker.css` для `<all_urls>` | Приемлемо, но позволяет фингерпринтинг: страница может определить наличие расширения по доступности ресурса (нет `use_dynamic_url`) |
| Разрешения | `tabs`, `scripting`, `storage`, `activeTab` + опциональный `<all_urls>` | `tabs` даёт доступ к URL/заголовкам всех вкладок постоянно — избыточно, частично покрывается `activeTab` |
| Целостность поставки | Подпись обеспечивает магазин (AMO/CWS); собственных проверок нет | Основной риск — компрометация аккаунта разработчика (кейс The Great Suspender) |

**V-12 (Средний). Избыточные постоянные разрешения + отсутствие явного CSP** — A05 Security
Misconfiguration.

### 2.5 Защита от DoS

Расширение не является сетевым сервисом, поэтому классический сетевой DoS неприменим.
Тестировался «локальный DoS» — исчерпание ресурсов браузера/диска и подвешивание UI.

**V-13 (Высокий). Неограниченный рост IndexedDB (disk exhaustion).**
Ни `saveThumbnail`, ни `CAPTURE_AND_SAVE` не проверяют число записей и суммарный объём.
Оценка: кроп ограничивает ширину 400 px (`cropImage`, `scale = min(1, 400/cw)`), типичный
JPEG q85 base64 ≈ 30–60 КБ; но при захвате без селектора сохраняется **полный кадр
видимой области** без даунскейла — на 4K-мониторе это 300–700 КБ на запись.
Автозахват работает по таймеру `setInterval(…, 2000)` (`content-autocapture.js:234`),
дедуп — только 30 с (`AUTO_CAPTURE_DEDUPE_MS`) и только по URL+title+selector.
Страница, которая раз в 30 с меняет `title` и `pushState`-URL, генерирует новую запись
каждые 30 секунд ⇒ ~120 записей/час ⇒ до ~80 МБ/час на одну вкладку. За сутки —
единицы гигабайт, до срабатывания квоты Origin Private Storage и отказа записи
(`DB Error`), плюс деградация всего профиля браузера.

**V-14 (Средний). Отсутствие rate limiting на привилегированных сообщениях.**
Обработчик не ограничивает частоту. Цикл `for(;;) runtime.sendMessage({type:"GET_ALL_THUMBNAILS"})`
со страницы заставляет воркер читать и сериализовать всю базу (десятки–сотни МБ base64)
в каждом ответе → 100 % CPU, «зависание» service worker, срыв дедупликации.

**V-15 (Средний). Дорогие операции в главном потоке рендера.**
`cropImage()` использует `Image` + `canvas` в контексте фона; `manager.js` рендерит карточки
пачками с `data:`-изображениями. При нескольких тысячах записей открытие менеджера
приводит к длительной заморозке UI (нет виртуализации, только «Load more»).

**V-16 (Низкий). ReDoS-подобная деградация через селектор.**
Пользовательский/подделанный селектор с `:has(… :not(…))` на глубоком DOM выполняется
каждые 2 секунды в каждой вкладке домена — устойчивая нагрузка на CPU (энергопотребление,
подтормаживание страниц).

## Задание № 3. Рекомендации по защите

### 3.1 Технические меры

**1. Валидация ввода и границы доверия (V-1, V-2, V-7)**

Проверять отправителя и не доверять данным из сообщения там, где их можно взять у браузера:

```js
const PRIVILEGED = new Set(["GET_ALL_THUMBNAILS","GET_ALL_SELECTORS",
  "CLEAR_ALL_THUMBNAILS","CLEAR_ALL_DOMAIN_CONFIGS","DELETE_THUMBNAIL","OPEN_MANAGER"]);

browser.runtime.onMessage.addListener((msg, sender, sendResponse) => {
  if (sender.id !== browser.runtime.id) return false;               // чужое расширение
  const fromExtensionPage = !sender.tab;                            // popup / manager
  if (PRIVILEGED.has(msg?.type) && !fromExtensionPage) {
    sendResponse({ ok: false, error: "forbidden" });                // не отдаём странице
    return true;
  }
  ...
});
```

Для `CAPTURE_AND_SAVE` — брать URL и hostname **только** из `sender.tab.url`, игнорируя
`msg.url`/`msg.hostname`:

```js
const tab = await browser.tabs.get(sender.tab.id);
const targetUrl = tab.url;
const hostname = new URL(tab.url).hostname;
```

Дополнительно: whitelist допустимых `msg.type`, схема-валидация полей (типы, длины,
`rect` — числа в разумных пределах), отказ по умолчанию (default deny).

**2. Валидация селекторов (V-9)**

```js
function isSafeSelector(sel) {
  if (typeof sel !== "string" || sel.length > 200) return false;
  try { document.createDocumentFragment().querySelector(sel); return true; }
  catch { return false; }
}
```
Проверять и при сохранении (`SAVE_SELECTOR`, `SAVE_DOMAIN_CONFIG`), и перед применением;
запретить `:has()` глубже одного уровня либо ограничить время исполнения.

**3. Безопасная генерация разметки (V-8)**

Строить SVG через `document.createElementNS` + `textContent`, либо экранировать:
```js
const esc = s => s.replace(/[&<>"']/g, c => ({"&":"&amp;","<":"&lt;",">":"&gt;",'"':"&quot;","'":"&#39;"}[c]));
```
Ввести в проект правило: никакой конкатенации строк для HTML/SVG; только DOM API
(в коде это уже почти везде соблюдено — надо зафиксировать линтером).

**4. Фильтрация URL при открытии (V-10)**

```js
const ALLOWED = new Set(["http:", "https:"]);
function safeOpen(url) {
  let u; try { u = new URL(url); } catch { return; }
  if (!ALLOWED.has(u.protocol)) return;
  browser.tabs.create({ url: u.href });
}
```

**5. Безопасное хранение (V-4, V-5)**

* Шифровать `dataUrl` перед записью через WebCrypto (AES‑GCM), ключ — из
  парольной фразы пользователя (PBKDF2/Argon2) либо неэкспортируемый ключ CryptoKey,
  сохранённый в IndexedDB; расшифровка только при открытом менеджере.
* Перенести селекторы и правила из `storage.sync` в `storage.local` (или сделать
  синхронизацию явной опцией с предупреждением) — домены не должны утекать в облако.
* Ввести TTL и автоочистку: удалять записи старше N дней по `timestamp`
  (индекс `timestamp` уже создан) через `alarms`.
* Домен-блоклист «никогда не захватывать» + автоматическое исключение
  приватных вкладок и страниц с формами ввода паролей.
* Не сохранять превью, если страница помечена `Cache-Control: no-store` или
  находится в режиме приватного просмотра.

**6. Генерация «безопасных сессий» (аналог в расширении)**

* Никаких предсказуемых ключей: если появится синхронизация между устройствами —
  идентификаторы устройства/сессии генерировать `crypto.getRandomValues`
  (≥128 бит энтропии), с ротацией и сроком жизни.
* При появлении серверной части: cookie только с `Secure`, `HttpOnly`,
  `SameSite=Strict`, `Path=/`, коротким TTL, регенерацией ID после смены прав,
  серверной инвалидацией при логауте, и обязательным HSTS.

**7. Противодействие DoS (V-13 – V-16)**

* Квоты хранилища: не более `MAX_THUMBS` (например, 500) записей и `MAX_BYTES`
  (например, 200 МБ); при превышении — LRU-вытеснение по индексу `timestamp`.
  Перед записью — `navigator.storage.estimate()` и отказ при `usage/quota > 0.8`.
* Жёсткий даунскейл всегда (не только при кропе): максимум 400×300 px, JPEG q60 —
  снижает объём записи в 5–10 раз.
* Rate limiting в обработчике: токен-бакет на `sender.tab.id`
  (например, 10 сообщений/с, 60/мин), с логированием превышений.
* Заменить `setInterval(…, 2000)` на событийную модель
  (`visibilitychange` + `MutationObserver` c debounce ≥ 1 с) и увеличить
  `AUTO_CAPTURE_DEDUPE_MS`; учитывать `document.hidden` и режим экономии батареи.
* В менеджере — виртуализованный список (IntersectionObserver + `loading="lazy"`),
  превью хранить как `Blob`/`ObjectURL`, а не base64 (экономия ~33 % и меньше нагрузка на GC).
* Тайм-аут на `cropImage` и на `querySelector` (через `requestIdleCallback`/AbortController).

**8. Конфигурация и компоненты (V-12)**

```json
"content_security_policy": {
  "extension_pages": "script-src 'self'; object-src 'none'; base-uri 'none'; frame-ancestors 'none'"
}
```
* Убрать постоянное `tabs`, где хватает `activeTab`; запрашивать `tabs` опционально.
* Для `web_accessible_resources` включить `use_dynamic_url: true` (анти-фингерпринтинг).
* Подключить SCA/секрет-сканирование в CI (`npm audit`, Dependabot, gitleaks),
  ESLint с правилами `no-unsanitized/property`, `no-eval`, статический анализ (CodeQL, Semgrep).
* Воспроизводимая сборка и подпись артефакта; проверка контрольной суммы перед публикацией.

**9. Логирование и мониторинг (V-11)**

* Вырезать `console.log` с URL/hostname в релизной сборке (флаг `DEBUG`, минификация с drop_console).
* Логировать только события безопасности: отклонённые сообщения, превышение rate limit,
  ошибки квоты — без персональных данных, с ограниченным буфером.

### 3.2 Организационные меры

1. **Политика безопасной разработки (SSDLC).** Моделирование угроз (STRIDE) на этапе
   проектирования каждой новой функции; чек-лист OWASP ASVS L2 и
   OWASP Top 10 при код-ревью; обязательный второй ревьюер для изменений в
   `background.js` и в обработчике сообщений.
2. **Политика минимальных привилегий.** Любое новое разрешение в `manifest.json`
   утверждается отдельно и сопровождается обоснованием в PR.
3. **Политика приватности и прозрачности.** Публичный документ: какие данные
   (скриншоты!) хранятся, где, сколько, как удалить. Экран первого запуска
   с явным согласием на автозахват (opt‑in, а не opt‑out) и с предупреждением,
   что превью могут содержать конфиденциальную информацию.
4. **Управление уязвимостями.** Файл `SECURITY.md` с контактом и SLA
   (ответ 72 ч, исправление критичных ≤ 14 дней), процесс координированного
   раскрытия, ведение CHANGELOG с пометками security.
5. **Защита цепочки поставки.** Обязательный 2FA/аппаратный ключ на аккаунтах
   разработчиков в AMO/CWS и GitHub, защищённая ветка `main`, подписанные коммиты,
   запрет добавления новых мейнтейнеров без ревью (прямой урок кейса The Great Suspender).
6. **Обучение пользователей.** Краткая инструкция в менеджере: не включать
   автозахват на банковских/корпоративных ресурсах, использовать доменный блоклист,
   периодически очищать хранилище, не устанавливать расширение на общий компьютер.
7. **Обучение команды.** Ежегодный тренинг по OWASP Top 10 и специфике
   безопасности WebExtensions; разбор реальных инцидентов (Equifax, SolarWinds,
   The Great Suspender) на внутренних семинарах.
8. **Регулярный аудит.** Раз в полгода — повторный white-box аудит и
   автоматическое сканирование в CI на каждый PR; ретест исправленных находок.

## Выводы

1. Проект демонстрирует **хорошую гигиену в части XSS**: во всей кодовой базе нет ни одного
   `innerHTML`/`eval`, вывод идёт через `textContent` и DOM API, подсветка поиска реализована
   безопасно. SQL-инъекции неприменимы архитектурно (IndexedDB, key-value), сторонних
   зависимостей нет — supply-chain риск минимален.
2. Основные риски лежат не в «классическом вводе», а в **границах доверия и приватности**:
   привилегированный обработчик сообщений без проверки отправителя (V-1, V-2, V-7) и
   незашифрованное бессрочное хранение скриншотов приватных страниц (V-4).
3. **Устойчивость к DoS низкая**: отсутствие квот на IndexedDB и rate limiting позволяет
   недоверенной странице исчерпать дисковую квоту и загрузить CPU (V-13, V-14).
4. Реализация мер P0–P1 закрывает все находки высокой и средней критичности и приводит
   расширение в соответствие с требованиями OWASP ASVS L2 в применимой части.
